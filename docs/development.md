# Development

The empty `:module` supplies library scaffolding. Target declarations, toolchains and publication
metadata belong to its build file; dependency versions belong to the version catalog and the
publication version belongs to `gradle.properties`. Rename module references when deriving a project.

## Verification

Run `./gradlew :verify` for formatting, JVM tests, generated documentation and release automation.
Run `./gradlew :verifyTargets --continue` for the Kotlin tests supported by the current host.
`verifyApple` and `verifyWindows` collect test runs from declared Apple and MinGW targets.
Target-family selection follows the Kotlin target declarations, including renamed targets.

CI assigns general tests to Ubuntu, Apple tests to macOS and MinGW tests to Windows. macOS and
Windows run only their platform-specific entry points. The Kotlin plugin determines which native
test binaries can execute on each host. Targets without a runnable test backend retain their
compilation and publication configuration. Derived projects provide device or emulator test setup
when their own test sources require it.

The template has no source tests. Successful empty task execution establishes scaffolding, not
runtime coverage. Run the derived project's tests before release. Gradle reuses valid outputs;
use focused task reruns when fresh execution is necessary.

## Build constraints

JS and Wasm retain executable binaries and their Kotlin-managed Node toolchains. Settings leaves
`repositoriesMode` unset because the web toolchain adds a Node distribution repository. Derived
projects commit the Yarn lock generated by `:kotlinUpgradeYarnLock`; this source-free template
keeps the lock outside its tracked scaffold. Review lock updates when web dependencies change.

Gradle and Kotlin compilation use separate daemon memory settings. The checked-in wrapper is
executable. The shared setup action configures Temurin and Gradle; setup-gradle owns wrapper
validation and caching. First-party GitHub and Gradle actions supply CI tools.

## Publication

Use `./gradlew :publishLocal` for local integration. Remote entry points require
`-PreleaseTag=<tag>`, a matching publication version and a clean checkout at that tag. Publication
tasks depend on the same checks even when invoked directly through the module.

Prepare a release with the manual draft workflow, selecting a tag, target branch or commit and an
optional previous tag. It uses GitHub-generated release notes as the initial editable draft and
preserves edits when resuming it. A new tag is created through release publication. The owner edits
and publishes the draft; version changes and draft preparation are separate from publication.

The publish workflow checks the release version and immutable event commit, then requires successful
push Test CI for that exact commit. It observes pending CI without rerunning tests. Publication
runs on macOS to build Apple artifacts. GitHub Packages runs with Gradle `--continue` so independent
publications are attempted; any failure blocks Maven Central. Publication workflows finish existing
uploads, while Test CI cancels superseded runs for the same branch or pull request.

Secrets provide signing keys and publication credentials. Tokens default to read-only content;
release drafts receive content write access and artifact uploads receive package write access.

These contracts follow the official [Kotlin native host support](https://kotlinlang.org/docs/native-target-support.html),
[GitHub Releases API](https://docs.github.com/en/rest/releases/releases),
[Gradle setup action](https://github.com/gradle/actions/blob/main/docs/setup-gradle.md) and
[Kotlin daemon settings](https://kotlinlang.org/docs/gradle-compilation-and-caches.html#the-kotlin-daemon-and-how-to-use-it-with-gradle).
